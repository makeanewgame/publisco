Kalan 2 kalem:

Kod tabanında SSE (Server-Sent Events) kullanımı olmadığı için şu an sömürülemez; büyük/riskli bir migration olduğundan bilinçli olarak ertelendi.

## Sorunlar (Buglar)
- [x] Vercel'de web deploy'u, `apps/api`'nin `postinstall` (`prisma generate`) script'i `PRISMA_DATABASE_URL` bulamadığı için install adımında patlıyordu — monorepo kökünde `pnpm install` çalıştığı için tüm workspace paketlerinin postinstall'ı tetikleniyor. `pnpm install --filter=<pkg>...` bunu ÇÖZMÜYOR: yerelde doğrulandı, filtreli install'da bile `apps/api`'nin kendi lifecycle script'i (ve tüm bağımlılıkları) yine kuruluyor — pnpm bu install modunda sibling workspace paketlerinin script'lerini atlamıyor. Asıl çözüm: `apps/api/package.json`'daki `postinstall`, `PRISMA_DATABASE_URL` set değilse `prisma generate`'i sessizce atlayacak şekilde korumaya alındı (`[ -z "$PRISMA_DATABASE_URL" ] && echo ... || prisma generate`). Vercel'deki custom Install Command (`--filter=web...`) artık gereksiz, gerekirse default'a geri alınabilir.
- [ ] `FloatingThemeToggle.tsx` hem `RootLayout.tsx`'te hem `Navbar.tsx`'te import ediliyor ama hiçbir yerde `<FloatingThemeToggle />` olarak render edilmiyor (ölü kod) — component'in kendi konumlama class'ı da eksik (`right-4 top-4` var ama `fixed`/`absolute` yok, render edilse bile ekranda konumlanmazdı). Kullanılacaksa gerçekten JSX'e eklenip pozisyon class'ı düzeltilmeli, kullanılmayacaksa silinmeli.
- [ ] Uygulama dili ingilizceyken satın alma penceresi türkçe açılıyor
- [x] Prod'da `/analyze` 403 ile patlıyordu: Modal logunda `download_pdf` içinde `403 Forbidden`. Geçici teşhis logu eklenip (sonra kaldırıldı) kök neden kesinleşti: `publisco-secrets` Modal secret'ındaki `BLOB_READ_WRITE_TOKEN` değeri literal `<` karakteriyle başlıyordu (`<vercel_blob_rw...`, 63 karakter) — yani placeholder/örnek metin parantezleriyle birlikte yanlışlıkla kopyalanmıştı, gerçek token değildi. `modal secret create ... --force` ile doğru token'la yeniden oluşturulup deploy edilince düzeldi (2026-08-11).
- [x] Yukarıdaki 403 düzelince aynı akışta `/convert` (tam pipeline) `process_chunk` içinde `404 Not Found` ile patlamaya başladı: `run_pipeline` (`modal_worker/main.py`), `plan.remote()` biter bitmez kaynak PDF'i `delete_blob(pdf_url)` ile Blob'dan siliyordu — ama map fazındaki her `process_chunk` container'ı aynı `pdf_url`'i kendi başına tekrar indirmeye çalışıyor (mimari gereği, bkz. CLAUDE.md "Map" açıklaması). Bu, önceden var olan bir sıralama hatasıydı; token 403'te maskelendiği için daha önce hiç tetiklenmemişti. Düzeltme: `delete_blob(pdf_url)` çağrısı `process_chunk.starmap(...)` (map fazı) tamamlandıktan sonraya taşındı.
- [x] Yukarıdaki 404 düzelince `upload_epub_to_blob` `400 Bad Request` ile patlamaya başladı: `"Cannot use public access on a private store."` — `modal_worker/main.py`'deki PUT isteği `x-vercel-blob-access` header'ı hiç göndermiyordu, Vercel Blob SDK'sı varsayılan olarak `public` deniyor ama store `private` olarak yapılandırılmış. Düzeltme: PUT isteğine `"x-vercel-blob-access": "private"` header'ı eklendi.
- [ ] Yukarıdaki 400 düzelince aynı job'da `run_pipeline`'ın sonunda attığı Vercel webhook'u (`post_vercel_webhook`) `404 {"detail":"Not Found"}` dönmeye başladı — bu gövde Nest'in değil FastAPI/Starlette'in varsayılan 404 formatı, yani `publisco-secrets`'taki `VERCEL_WEBHOOK_URL` gerçek Nest API'sine değil bir FastAPI uç noktasına (büyük ihtimalle Modal worker'ın kendi `MODAL_ENDPOINT_URL`'ine) işaret ediyordu. Bu aynı zamanda Modal'ın kendi loglarındaki tekrarlayan `POST / -> 404`'ü de açıklıyor (webhook kendi kendine POST atıyor). `curl -X POST https://api.publisco.com/api/webhooks/modal-result` ile doğru URL doğrulandı (401 "Invalid webhook signature" döndü — Nest doğru route'ta canlı). Kod tarafında düzeltilecek bir şey yok; `publisco-secrets`'taki `VERCEL_WEBHOOK_URL`'in Modal dashboard'undan `https://api.publisco.com/api/webhooks/modal-result` olarak güncellenmesi gerekiyor (kullanıcıya iletildi, henüz teyit bekleniyor).
